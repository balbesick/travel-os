# Stakeholders — Заинтересованные стороны

Этот файл подготовлен в рамках задачи #3 — определение стейкхолдеров и их интересов.

## Список заинтересованных сторон

### Внутренние

- **Основатель (Founder)** — видение, PMF, монетизация, инвестиции, приоритеты.
- **Команда разработки** — ясные требования, стабильная архитектура, документированные API, контроль техдолга.
- **Дизайн / продукт** — исследования пользователей, интерфейсы, KPI продуктовой успешности.
- **Операции / поддержка** — мониторинг, логирование, процессы поддержки и SLA.

### Внешние

- **Путешественники (энд‑юзеры)** — простой поиск и бронирование, доверие (отзывы, рейтинги), приватность, мобильность, локализация, поддержка.
- **Локальные гиды** — поток клиентов, прозрачные условия оплаты, управление расписанием и профилем, справедливая комиссия.
- **Отели / B2B‑партнёры** — интеграции бронирования, управление доступностью, отчётность и договоры.
- **Платёжные провайдеры** — безопасные транзакции, соответствие стандартам (PCI).
- **Регуляторы / законы (локальные, GDPR/CCPA)** — защита персональных данных, налоговая/лицензирование.
- **Инвесторы** — метрики роста, unit‑economics, прогресс по вехам.
- **App Stores / платформы распространения** — требования к приватности, хранению данных, разрешениям.
- **Локальные сообщества / власти** — влияние туризма, соблюдение местных правил и ограничений.

## Матрица интересов (кратко)

### Путешественники
- Ожидания: быстрый поиск, понятное бронирование, безопасность транзакций, поддержка.
- Боли: потеря времени, ненадёжные гиды, непрозрачные комиссии.
- Решение: единый UX, рейтинги и верификация гидов, прозрачная цена, гарантия возврата.

### Локальные гиды
- Ожидания: доступ к клиентам, удобный календарь, своевременные выплаты.
- Боли: административная нагрузка, неплатёжеспособные клиенты.
- Решение: встроенная система расписаний, предоплаты/эскроу, простая панель управления.

### Отели / B2B
- Ожидания: синхронизация наличия, управление тарифами, API/портал.
- Боли: двойные брони, сложность интеграции.
- Решение: стандартные интеграции (OTA/Channel Manager), webhook’и, отчёты.

### Команда разработки
- Ожидания: ясные требования, тестовые сценарии, предсказуемый roadmap.
- Боли: смена приоритетов, нарастающий техдолг.
- Решение: приоритеты по ценности для ключевых стейкхолдеров, архитектурные принципы (модули, контрактное тестирование).

### Основатель / инвесторы
- Ожидания: рост, метрики, контроль затрат.
- Боли: медленный рост, плохие unit‑metrics.
- Решение: фокус на фичах с высокой ROI, метрики в dashboard.

## Ограничения и требования (важные для архитектуры и процесса)

- Законодательство о защите данных: GDPR (ЕС), возможные локальные законы по хранению/переносу данных.
- Требования магазинов приложений: прозрачность сбора данных, политика конфиденциальности, разрешения (App Store / Google Play).
- Платежи: соответствие PCI DSS при хранении/обработке карт; KYC/AML для выплат гиду (в зависимости от юрисдикции).
- Договорные/налоговые требования для B2B‑партнёров (учёт комиссий, VAT).
- Безопасность и ответственность: страхование ответственности гидов/поставщиков услуг (требование к партнёрам).
- Доступность: базовый уровень WCAG для критичных экранов.
- Локализация: язык/валюта/формат дат для целевых рынков.
- Интеграции: стандарты OTA и channel‑managers, версии API.
- Масштабируемость: проектировать сервисы так, чтобы ключевые пути (поиск, бронирование, платежи) были горизонтально масштабируемыми.
- Ограничения инфраструктуры: возможные требования к хранению данных по регионам (data residency).
